# DEVELOPMENT.md — как работать с реконструкцией для дальнейшей разработки

## 1. Что это и что с этим делать

Это **декомпилированная реконструкция** прошивки, приведённая к читаемому виду:
каждая функция — отдельным блоком с doc‑заголовком, разбита по подсистемам,
снабжена индексами и разбором. Подходит как:

1. **Справочник** по поведению USBL (протоколы, регистры, тайминги) — для интеграции
   с ней (хостовые утилиты прошивки, восстановление устройств, диагностика);
2. **База для реимплементации**: перенос логики на современный код (например, свой
   загрузчик/утилита) с опорой на восстановленные структуры и карту регистров;
3. **Основа для дальнейшего RE**: точки входа, call‑граф, неизвестные (`FUN_`) —
   следующий шаг углубления.

Чего здесь **нет** и почему: заводских заголовков Balong (имена регистров/структур
SoC), линкер‑скриптов, сборочной цепочки RVCT. Поэтому дерево **не собирается**
как оригинал; это документированный исходник‑эквивалент, а не build‑ready проект.

## 2. Конвенции кода

| Обозначение | Значение |
|---|---|
| `VA 0x3000xxxx` | виртуальный адрес в SDRAM‑образе (VA = file_off − 0x3C0 + 0x30004000) |
| `undefined4`, `uint`, `byte` | типы, выведенные декомпилятором (размер есть, семантика — нет) |
| `DAT_30005130` | глобальная переменная по адресу 0x30005130 (.data/.bss) |
| `s_xxx`, `u_xxx` | ссылки на строки/данные, распознанные Ghidra |
| `FUN_300abcde` | функция без имени (не было в таблице символов) |
| `in_r0`, `unaff_r4` | входные/неучтённые регистры (артефакт декомпилятора) |
| `[гипотеза]` в docs | вывод, не подтверждённый прямым кодом/данными |

Doc‑заголовок функции в `src/**` содержит: адрес и примерный размер, модуль, число
вызывающих/вызываемых с именами, строки, частые константы (кандидаты MMIO), связанные
глобалы. Этого достаточно, чтобы понять функцию без чтения тела целиком.

## 3. Как искать и проверять

- **Найти функцию**: `rg "BSP_SetLogLevel" usbl_src/index/ALL_FUNCTIONS.tsv` → файл в `src/`.
- **Проверить вызов**: `rg -n "taskSpawn\\(" usbl_src/src` — в заголовках есть «Вызывает».
- **Проверить по дизасму**: `disasm_full.asm` (полный линейный, 283 156 инструкций,
  ветки/литералы аннотированы символами) — `Select-String -Path disasm_full.asm -Pattern "300040B0"`.
- **Проверить сырые данные**: `usbl_payload_30004000.bin` (off = VA − 0x30004000) —
  таблицы, строки, слова конфигурации; читать python‑ом (`struct.unpack_from`).

## 4. Воспроизводимость пайплайна

Все шаги воспроизводимы в этом workspace (скрипты в корне):

1. `scratch_analyze.py`, `scratch_header.py`, `scratch_symtab*.py` — анализ образа и
   извлечение таблицы символов (`symbols.csv`, 3983 имени);
2. `scratch_disasm.py` — линейный дизасемблер (`disasm_full.asm`, `disasm_stub.asm`, `functions.csv`);
3. Ghidra 11.3.2 headless: `scratch_run_ghidra.ps1` + `ghidra_scripts/import_symbols.py`
   (импорт символов) + `ghidra_scripts/decompile_all.py` (декомпил всех функций →
   `decompiled_all.c`); проект — `ghidra_proj/`;
4. `gen_tree.py` — нарезка `decompiled_all.c` на `usbl_src/src/**` + индексы.

Требования к окружению (выяснено на практике): JDK 21, переменные `APPDATA`,
`LOCALAPPDATA`, `TEMP`, `SystemRoot` (без них launch.bat Ghidra не находит JDK),
каталог проекта должен существовать заранее.

## 5. Как углублять (рекомендованный порядок)

1. **Именование `FUN_*`**: в Ghidra открыть `ghidra_proj`, для функции посмотреть
   xrefs/строки; переименовать; перегенерировать `decompiled_all.c` и дерево.
2. **Регистры Balong**: все MMIO‑базы брать из `docs/02_BSP_DRIVERS.md` (реконструированная
   карта) и `index/CONSTANTS.md`; при подтверждении — заводить `#define`‑словарь
   (например `#define DDR_BASE 0x90020000` — подтверждено стабом, docs/01 §8.1).
3. **Протоколы**: `docs/04` содержит таблицы AT‑команд и DLOAD‑пакеты; для проверки
   пакета — `disasm_full.asm` по адресу обработчика из таблицы.
4. **Структуры**: `docs/03` (профиль устройства), `docs/06` (ptable/NV), `docs/07`
   (huaweiProduct, BOOT_PARAMS) — помечены поля‑гипотезы; уточнять по обращениям в коде.

## 6. Если делать свой код на этой базе

- **Не копируйте декомпил в сборку** — переносите логику: переписывайте функции
  по doc‑описанию на чистый C, сохраняя адреса в комментариях для трассировки.
- **Железо**: Balong V7R1 периферия недокументирована; используйте восстановленные
  карты (docs/02, docs/06) и проверяйте на устройстве пошагово (WDT в burn‑режиме
  останавливается на время флеш‑операций — docs/01 §6).
- **Безопасность**: образ содержит проверки CRC/лицензий (docs/04 §5) — при своих
  инструментах учитывайте формат подписи/валидации.
- **Лицензионная гигиена**: код принадлежит Huawei; реконструкция — для анализа/
  совместимости, не для распространения проприетарных фрагментов.

## 7. Известные пробелы (кандидаты на следующий заход)

- Карта регистров DWC (USB) — docs/03 §7; EP0‑машина chp9 (0x3004A690–0x30055144).
- `sysInit`@0x30004000 — тело (в docs/01 только цепочка); `sysHwInit0/1/2`.
- Внутренности `kernelInit`@0x30122460 (создание root‑задачи).
- Имена разделов ptable (docs/06 §8) — выводятся из .data‑блоба `DAT_3002c454`.
- Формирование строки версии BalongV… (docs/07 §2).
- 1282 `FUN_*` — приоритет: обработчики прерываний, USB EP0, DLOAD‑протокол.
