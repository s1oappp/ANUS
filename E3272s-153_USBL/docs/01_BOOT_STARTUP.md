# 01. Процесс загрузки usblsafe-327x.bin (Balong V7R1 / HI6920, VxWorks 6.8)

**Статус:** черновик v1, дописывается правками (маркеры `<!-- FILL:* -->` заменяются по результатам контрольных чтений).
**Дата:** 2026-10-19.
**Объект:** `usblsafe-327x.bin` — USB-загрузчик (USBL) Huawei Balong V7R1, чип HI6920 (ARM Cortex-A9), тело — VxWorks 6.8.
**Правило пересчёта адресов:** `VA = file_offset − 0x3C0 + 0x30004000`; обратное: `file_offset = VA − 0x30004000 + 0x3C0`.

Источники (уровни доказательности):
- **[A]** первичный код: `disasm_stub.asm` (дизасемблер стаба), `usbl_stub_2ffe4000.bin`, `usbl_payload_30004000.bin`, `decompiled_all.c`;
- **[B]** индекс функций: `usbl_src/index/ALL_FUNCTIONS.tsv` (адрес, имя, модуль, исходник реконструкции, размер);
- **[C]** предыдущий отчёт: `usblsafe-327x-report.md`;

## 0. Резюме

Загрузка двухступенчатая. Ступень 1 — «стаб» в IRAM по адресу **0x2FFE4000** (файл 0x54–0x3BF): единственная функция — подготовка внешней памяти/DDR-блока у базы **0x7771E000** [D: значение литерала 0x2FFE4334, подтверждается правкой; смещения регистров — факт [A]] и системного блока **0x90000000**, с тремя поллингами готовности и задержкой; после настройки стаб **возвращается** вызывающему коду (`pop {r0–r5}; mov pc, lr` @0x2FFE432C–0x2FFE4330) — цикла копирования тела в стабе **нет** [A]. Ступень 2 — тело VxWorks в SDRAM **0x30004000**: `sysInit`@0x30004000 → `usrInit`@0x30040280 (кэш/векторы/`sysHwInit`) → `usrKernelInit`@0x3003FBD8 → `kernelInit`@0x30122460 → `usrRoot`@0x300404BC (пул памяти, MMU, sysClk, IOS) → `usrAppInit`-блок (NAND/YAFFS/PMU/LED/WDT/dload/USB) и три задачи `taskSpawn` [A][B].

## 1. Образ и карта адресов

| Объект | Файл | VA | Комментарий |
|---|---|---|---|
| Заголовок USBL | 0x000–0x053 | — | +0x2C = **0x2FFE4000** (точка входа стаба), +0x3C = **0x30004000** (адрес загрузки тела) — `usblsafe-327x-report.md:36,40` [C] |
| Стаб | 0x054–0x3BF | **0x2FFE4000–0x2FFE43BF** | on-chip RAM (IRAM) SoC [C: report.md:36] |
| Тело (VxWorks) | 0x3C0–… | **0x30004000–0x301B018C** | код 0x30004000–0x3012E06B (~1,22 МБ, 3889 функций) — report.md:55 [C] |

Стаб исполняется в IRAM, тело исполняется из SDRAM по 0x30004000 [C]. Из этого следует [D]: стаб получает управление **до** записи тела в SDRAM (иначе телу неоткуда исполняться — DDR должен быть поднят заранее); собственно перенос тела в 0x30004000 выполняет вызывающая сторона (ROM-загрузчик / хост-протокол USBL), а не стаб.

## 2. Этап I. Стаб 0x2FFE4000 (инициализация памяти)

Источник: `disasm_stub.asm` (полный, 0x2FFE4000–0x2FFE435C) [A].

### 2.1. Точка входа и служебная зона

- **0x2FFE4000** `push {r0–r5}`; **0x2FFE4004** `b 0x2FFE4144` — вход сразу уходит в основную процедуру; возвратный путь у неё собственный.
- **0x2FFE4008–0x2FFE410C** — нули (выравнивающая/резервная зона, 63 слова).
- **0x2FFE4110–0x2FFE4140** — 12 слов данных, дизассемблируются как бессмысленные инструкции → данные (назначение не установлено, см. §7).
- Основная процедура: **0x2FFE4144–0x2FFE4330**; литеральный пул: **0x2FFE4334–0x2FFE4368**; хвост данных до 0x2FFE43BF [A].

### 2.2. Процедура 0x2FFE4144: базовые регистры

| Адрес | Инструкция | Эффект |
|---|---|---|
| 0x2FFE4144 | `mov r1, #0x90000000` | r1 = база системного блока (PMU/CRG, имя регистра не восстановлено) |
| 0x2FFE4148–0x2FFE4154 | `ldr/and/mvn/str` | `[0x90000038] &= ~0x20000` — снять бит 17 |
| 0x2FFE4158 | `ldr r1, [pc, #0x1D4]` | r1 = слово **0x2FFE4334** → база DDR-блока (ожидается **0x7771E000**; подтверждение — правка §2.4) |
| 0x2FFE415C–0x2FFE4160 | `mov r2,#0x1D; str` | `[DDR+0x810] = 0x1D` |
| 0x2FFE4164–0x2FFE41C0 | цикл записей (проход 1) | одно значение (слово **0x2FFE4338**) в `[DDR+0x430]`, `[+0x434]`, `[+0x440]…[+0x464]` (шаг 4, смещения 0x438/0x43C пропущены — 12 записей) |
| 0x2FFE41C4–0x2FFE4220 | проход 2 | другое значение (слово **0x2FFE433C**) в те же 12 смещений |
| 0x2FFE4224–0x2FFE4228 | | `[DDR+0x58] = слово 0x2FFE4340` |
| 0x2FFE422C–0x2FFE4230 | `mov r2,#0; str` | `[DDR+4] = 0` |

Два прохода записи одной и той же группы PHY-регистров двумя разными значениями — характерный паттерн настройки DDR PHY (уровень/калибровка) [D]. Записи идут в один и тот же r1 → один DDR-контроллер; второй чип/канал в стабе не настраивается [A].

### 2.3. Поллинги, задержки, финальные записи

| Адрес | Код | Смысл |
|---|---|---|
| 0x2FFE4234–0x2FFE4240 | `ldr [r1,#0x808]; and #0x80000000; bne` | ждать установки бита 31 в `[DDR+0x808]` |
| 0x2FFE4244–0x2FFE4250 | | `[DDR+0x804] = 0x6B`; `[DDR+0x800] = 0x40000000` |
| 0x2FFE4254–0x2FFE4260 | | снова ждать бит 31 `[DDR+0x808]` |
| 0x2FFE4264–0x2FFE4270 | `ldr r3,[pc,#0xD8]; subs/bne` | холостой цикл задержки, счётчик = слово **0x2FFE4344** |
| 0x2FFE4274–0x2FFE42B8 | серия `str` | `[DDR+0x14]=0x32`; `[+0x18]=0`; `[+0x1C]=сл.0x2FFE4348`; `[+0x20]=сл.0x2FFE434C`; `[+0x2C]=[+0x30]=[+0x34]=[+0x38]=0x22`; `[+0x40]=0x30000000` |
| 0x2FFE42BC–0x2FFE42E0 | | `[+0x50]=сл.0x2FFE4350`; `[+0x54]=сл.0x2FFE4354`; `[+0x58]=сл.0x2FFE4358`; `[+0x5C]=сл.0x2FFE435C`; `[+0xAC]=сл.0x2FFE4360` |
| 0x2FFE42E4–0x2FFE42E8 | `mov r2,#1; str` | `[DDR+8] = 1` (старт/разрешение) |
| 0x2FFE42EC–0x2FFE42F8 | | ждать бит 3 в `[DDR+0]` |
| 0x2FFE42FC–0x2FFE4300 | | `[DDR+0x20] = сл.0x2FFE4364` (перезапись) |
| 0x2FFE4304–0x2FFE4308 | | `[DDR+0xF8] = 1` |
| 0x2FFE430C–0x2FFE4314 | `mov r1,#0x90000000; mov r2,#0x30000000; str` | `[0x90000470] = 0x30000000` — база SDRAM |
| 0x2FFE4318–0x2FFE431C | | `[0x90000474] = сл.0x2FFE4368` |
| 0x2FFE4320–0x2FFE4328 | `ldr/orr #1/str` | `[0x90000400] |= 1` |
| 0x2FFE432C–0x2FFE4330 | `pop {r0–r5}; mov pc, lr` | **возврат** в вызывающий (ROM) код |

`[DDR+0x40] = 0x30000000` и `[0x90000470] = 0x30000000` фиксируют базу SDRAM — согласуется с адресом загрузки тела из заголовка (+0x3C) [A]+[C].

### 2.4. Литеральный пул стаба (VA → назначение → значение)

Считывание слов из `usbl_stub_2ffe4000.bin` (файл начинается с VA 0x2FFE4000, т.е. `off = VA − 0x2FFE4000`):

| Слово VA | Куда пишется | Значение |
|---|---|---|
| 0x2FFE4334 | r1 — база DDR-блока | **0x90020000** |

Показания литерального пула (чтение `usbl_stub_2ffe4000.bin`): база DDR‑блока — **0x90020000**, а не 0x7771E000; следовательно все «[DDR+смещ]» из §2.2–§2.3 — это **0x90020000+смещение**. Константа 0x7771E000 — отдельный литерал (VA 0x2FFE4340), назначение не установлено (см. §7).

### 2.5. Выводы по стабу

1. Стаб — **инициализатор DDR/контроллера памяти**, возвращает управление (`mov pc, lr`), никуда не прыгает [A].
2. **Копирование тела в стабе отсутствует**: ни одного цикла `ldr/str` парного копирования, ни обращения к 0x30004000 как к адресу назначения копии (0x30000000 используется как значение конфигурационных регистров) [A]. Перенос тела выполняет внешняя сторона (ROM/хост по USBL-протоколу, адрес из заголовка +0x3C) [D, согласуется с report.md:47–49 «Мини-загрузчик SoC … инициализация контроллеров (записи в регистры PLL/DDR, поллинги готовности…)»].
3. Ровно три ожидания готовности (0x808.31 ×2, [DDR+0].3 ×1) и одна программная задержка [A].

## 3. Этап II. sysInit → usrInit (старт VxWorks)

Все адреса — `usbl_src/index/ALL_FUNCTIONS.tsv` [B], тела — `decompiled_all.c` [A], реконструкция — `usbl_src/src/boot/boot_01.c` [B].

### 3.2. Что делает каждая ступень

- **sysInit@0x30004000** — точка входа тела. Содержимое в `boot_01.c` только сигнатурой (`void sysInit(void)`); детального разбора не проводилось (см. §7-1) [B].
- **sysStart** — earliest C-точка: обнуление BSS (`bzero`), `intVecBaseSet` (база векторов прерываний), `sysHwInit0` [A: boot_01.c:287–295].
- **sysHwInit0@0x30004314** (data/data_01.c, 32 Б) — самая ранняя аппаратная инициализация до кэша [B]. Тело миниатюрное — детализация в §7-2.
- **usrInit@0x30040280** (116 Б) — тело выписано дословно [A: decompiled_all.c:34911–34929]: `sysStart` → `cacheLibInit(2,2)` (I+D кэши) → `excVecInit()` (вектор исключений) → `sysHwInit` → `usrCacheEnable()` → инициализация objLib/classLib/semLib/kernelBase/vxMemProbe → `usrKernelInit(0)`.
- **sysHwInit@0x30004334** (boot/boot_01.c, 44 Б) — аппаратная инициализация после включения векторов [B][A: boot_01.c:204–211]. GIC/контроллер прерываний: внутри 44 байт мало места — вероятно, инициализация GIC выполняется в `intVecBaseSet`/`excVecInit` (см. §7-3).
- **MMU**: включение MMU/кэшей отложено до `usrMmuInit`@0x3003FCE4, вызываемого уже из `usrRoot` [A: decompiled_all.c:35095; B].

## 4. Этап III. usrKernelInit → kernelInit → usrRoot

Ядрообразующая функция VxWorks: создаёт root-задачу `usrRoot` на уже работающем планировщике (передача управления в многозадачный режим). Параметр-функция корня — через DAT_30040608 (см. §6). Деталь тело kernelInit в этом прогоне не разбиралось (§7-4).

## 6. Порядок инициализации драйверов / IOS

**Ядро → IOS → приложения** (по телу usrRoot §4.3):
1. `usrIosCoreInit()` — базовая IOS; реальная работа с драйверами — `iosInit`@0x300E9308 (kernel/kernel_04.c, 784 Б) [B]. Вызывается из usrRoot **до** `usrKernelExtraInit`/`usrIosExtraInit`.
2. `usrIosExtraInit()` — дополнительные драйверы IOS.
3. `usrToolsInit()`, затем `usrAppInit()`@0x30005018 [B].

**Прикладной блок (decompiled_all.c:931–973)** — последовательность:
1. `logMsg` при ошибке предыдущего шага (:931–933);
2. `nand_init()` (:934);
3. проверка `_DAT_2ffffffc != DAT_3000511c` → `nand_erase_all()` (:938–939) — затирание NAND при несовпадении контрольного слова;
4. `BSP_WDT_Feed_Force()` (:941), `BSP_WDT_Stop()` (:942);
5. `yaffsInit()` (:943);
6. `BSP_WDT_Resume()` (:947), `BSP_WDT_Feed_Force()` (:948);
7. `BSP_PMU_BoardInit()` (:949);
8. `BSP_TLED_LedInit()` (:950);
9. `WDT_Init()` (:954) — `WDT_Init`@0x30007448 [B];
10. `BSP_WDT_Stop()` (:958), `power_off_clearup_flag()` (:959);
11. `dloadInit()` (:960) — подсистема скачивания (`dload/dload_01.c`: `TFUP_DloadTask`@0x30077164 [B]; буфер `g_stDloadWriteBuffer`, строка ошибки @firmware 0x148184);
12. `USB_UnReset()` (:961), сброс слов DAT_300050b8/DAT_3000512c (:962–963);
13. `taskSpawn(tUSBTask)` (:964);
14. если `TFUP_getTFUpdateFlag()==1` → `TFUP_CheckInit()`, `sdmmcISRInit()` (:965–969);
15. `taskSpawn(tDloadTask)` (:970), `taskSpawn(tIdletask)` (:971).

Порядок WDT-вызовов вокруг yaffsInit показывает, что долгие флеш-операции выполняются при **остановленном** аппаратном WDT с ручным фидом [A+D].

## 7. Открытые вопросы

1. **sysInit@0x30004000**: фактическое содержимое (настройка SP/режима, прыжок в usrInit) — нужен дизасем 0x30004000–0x30004314; в реконструкции есть только сигнатура.
2. **sysHwInit0@0x30004314 (32 Б), sysHwInit@0x30004334 (44 Б), sysHwInit2@0x30004360 (92 Б)**: малые тела; какие именно регистры пишут — не восстановлено в этом прогоне.
3. **GIC**: точное место инициализации контроллера прерываний (кандидаты: `intVecBaseSet` из sysStart, `excVecInit`, `intVBRSet`@boot_01.c [B]).
4. **kernelInit@0x30122460**: внутренняя механика создания root-задачи (772 Б) — не разобрана.
5. **Назначение слов данных стаба 0x2FFE4110–0x2FFE4140**.
6. **Семантика регистров DDR-блока 0x7771E000+** (0x430–0x464, 0x800/804/808/810) — имена регистров Balong не восстановлены [C: report.md:129].
7. **tShell0**: конкретные prio/stack при создании (читаются из конфиг-слов shellLib) — найти вызов `shellGenericInit` и его аргументы.
8. **tSoftTimerHandle**: сайт спавна — см. правку §6.
9. Второй проход записи PHY (§2.2) — зачем два значения в одну группу регистров (write-leveling / два этапа калибровки) — предположение [D].
