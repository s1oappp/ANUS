# 09. Порт Linux на E3272s‑153: база из загрузчика и план работ

> Синтез: факты из USBL (docs/08, docs/01–07) + публичные источники (веб‑разведка 2026‑10‑19,
> ссылки в §8). Цель — практический маршрут «свой Linux на E3272s‑153».

## 2. Архитектурная реальность платформы (важно до начала работ)

По публичным данным [web: balong_series.md]:

- Balong V7 = **2×ARMv7** (одно ядро — Linux, второе — VxWorks‑модем) + **Cortex‑M3** (boot/M3)
  + **ConnX BBE16 DSP**. Штатно на E3272 уже работает **Linux 2.6.35.7** (UI/сеть) и
  VxWorks (модемная логика) — то есть «порт Linux» — это не «с нуля на голое железо»,
  а **замена/расширение штатного Linux‑ядра** на уже работающей плате.
- V7R1/E3272: **128 МБ RAM** (под штатным Linux свободно ~15 МБ), **256 МБ NAND**,
  ARMv7 **без FPU** (soft‑float!), Wi‑Fi BCM43241 (в модеме может отсутствовать).
- Mainline **не поддерживает** Hi6920/Hi693x; формально ближайший каркас — `mach‑hisi`
  с HiP01 (2×Cortex‑A9, DTS‑пример) — использовать как скелет, не как готовый порт.

Вывод: реалистичная цель — **своё Linux‑ядро вместо штатного Linux‑раздела**, с сохранением
VxWorks‑модема (иначе LTE не заработает: модемный стек — проприетарный бинарь на втором ядре).

### 2.1. Карта флеша — уже расшифрована из образа (docs/11_FLASH_MAP.md)

Дефолтная ptable извлечена из .data‑блоба (DAT_3002c454 → 0x3018000C), 17 разделов:

| Раздел | Offset | Size | Type | Роль для порта |
|---|---|---|---|---|
| BootLoad | 0x00000000 | 128 КБ | 0x101 | USBL (наш файл) — **одна копия, A/B нет** |
| NvBackLTE / NvBackGU | 0x20000 / 0x1A0000 | 1.5/1 МБ | 0x10D/0x10E | резервные NV |
| BootRom ×2 | 0x2A0000 / 0x4A0000 | 2 МБ | 0x102 | **A/B‑пара bootrom** |
| VxWorks | 0x6A0000 | 32 МБ | 0x103 | модемный стек — НЕ ТРОГАТЬ |
| /yaffs0 | 0x26A0000 | 12 МБ | 0x106 | данные |
| FastBoot | 0x32A0000 | 384 КБ | 0x104 | fastboot‑загрузчик |
| **kernel** | **0x3300000** | **3 МБ** | **0x105** | **замена ядра Linux** |
| /yaffs1 (System) | 0x3600000 | 28 МБ | 0x107 | rootfs |
| /yaffs2..6 | 0x5200000 | дин. | 0x108–0x113 | App/WebUI и пр. |
| cdromiso | 0x5200000 | 174 МБ | 0x10C | виртуальный CD‑ROM (до 0x10000000 = ровно 256 МБ NAND) |

Ссылки на типы совпадают с кодами `balongflash` (`_R1`‑набор) — прошивальщик применим напрямую.

## 3. Три стратегии (и рекомендация)

**A. Замена штатного Linux‑ядра (рекомендуется как цель).**
Своё ядро ставится в тот же раздел, откуда штатно грузится Linux (по публичным данным
для V7R1‑семейства это отдельный kernel‑раздел; точное имя — из вашего ptable, §5).
Плюс: штатный boot‑путь (M3/bootrom) остаётся, VxWorks‑модем живёт.
Минус: нужно поднять драйверы (NAND/MTD, DWC gadget, SD, PMU) — объём работы большой.

**B. Загрузка ядра «сверху» через USBL/fastboot‑подобный путь.**
Прецедент есть на V7R11 (hitechshell: raminit + payload → fastboot → boot.img), но
адреса (payload 0x57d00000, mem=0x3300000, base 0x54c08000) **непереносимы** на V7R1.
Для E3272 USBL сам является инструментом: shell/DLOAD позволяют залить payload в RAM
и передать управление. Плюс: быстрый цикл экспериментов без риска для NAND.
Минус: нет публичного репорта для V7R1; нужен свой raminit/payload‑загрузчик.

**C. Гибрид (минимальный путь к «работающему» устройству).**
Своё Linux‑ядро + штатный VxWorks‑модем + IPC (как в штатной архитектуре: два ARMv7,
разделяемая память). Это то, как устройство спроектировано; «свой Linux» здесь — замена
UI/сетевого ядра, а не модемного.

**Рекомендация:** начать с **B** (безопасные эксперименты, быстрый UART‑консольный цикл),
вести к **A/C** (постоянная загрузка). Раздел USBL не трогать до подтверждения A/B‑пары
(docs/10 §5.8).

## 4. Что нужно сделать (фазы)

### Фаза 0 — доступ и дампы (1–2 дня)
1. UART‑консоль: найти на плате TX/RX/GND тестпоинты UART0 (0x90007000, 115200) —
   после старта USBL это stdout VxWorks (docs/05 §3), значит консоль уже работает.
2. Полный дамп NAND и ptable (через shell `ptable_show`/чтение 0x1E000 или DLOAD) —
   сохранить офлайн; разобрать ptable сплиттером (balong‑raw‑dump‑tools) и получить
   **точные имена/смещения разделов** (в т.ч. имя Linux‑ядра и USBL).
3. Зафиксировать факты с живого устройства: `BSP_GetSupportBands`, версии
   (`AT^DLOADVER?`/`AT^DLOADINFO?`), `BSP_GetBuildVersion`, значение 0x2ffffffc.

### Фаза 1 — инструменты и «мигалка» (неделя)
1. Toolchain: ARMv7‑A **soft‑float** (arm-none‑eabi‑gcc или clang `-mfloat-abi=soft`;
   FPU нет — docs/08 §1).
2. Минимальный payload: включить клок UART (CRG 0x90000000+), настроить PL011
   (0x90007000, 48 МГц, 115200), вывести строку, вернуться. Проверка цикла
   «залил → увидел в консоли → жив».
3. Свой raminit‑подобный загрузчик (по образцу hitechshell, но со своими адресами):
   цель — грузить произвольный бинарь в SDRAM и передавать управление.

### Фаза 2 — ядро (основная работа)
1. База: **vendor Linux 2.6.35.7** из GPL‑зеркала Huawei (там реальные драйверы Balong)
   либо mainline + скелет HiP01‑DTS (mach‑hisi) — решать после чтения GPL‑исходников.
2. Драйверы первой волны: PL011 (uart), GIC (irq‑chip), arch timer,
   **NAND/MTD** (nandc: база регистров — открытый вопрос docs/06 §8),
   DWC gadget (USB‑ethernet/serial для отладки), SD/MMC (IRQ 108).
3. Загрузка: initramfs (RAM‑бюджет под Linux ~15 МБ! — docs/02/08), cmdline
   `console=ttyAMA0,115200`.

### Фаза 3 — rootfs и сеть
1. Минимальный initramfs (busybox), затем persistent rootfs на NAND (mtdblock).
2. Сеть: USB‑gadget RNDIS/ECM (DWC уже есть) — на время bring‑up достаточно.

### Фаза 4 — LTE
1. Не поднимать модем с нуля: оставить штатный **VxWorks‑модем** на втором ядре,
   взаимодействие — через разделяемую память/IPC (как в штатной прошивке).
2. Альтернатива для экспериментов: AT‑канал через USB (docs/04) — модем живёт отдельно.

## 5. Ловушки (обязательно прочитать перед первым патчем)

1. **`nand_erase_all` по слову 0x2ffffffc** — несовпадение маркера при старте USBL
   стирает весь NAND (docs/10 §1.6). Не менять это слово и не ломать путь мягкого ребута.
2. **Раздел USBL в единственном экземпляре?** A/B‑пара не подтверждена (docs/10 §4.2) —
   до выяснения не перепрошивать сам загрузчик.
3. **Lic/CRC на TF‑пути** (`TFUP_ValidateCRCWithLic`) — при обновлении с TF‑карты
   образ должен пройти проверки; USB‑путь этих проверок не содержит (docs/10 §1.1).
4. **Нет FPU** — весь код soft‑float; тяжёлые вычисления медленные, NEON нет.
5. **15 МБ свободной RAM** под Linux на штатной архитектуре — бюджет initramfs и
   драйверов жёсткий.
6. **Имена разделов — решено из образа** (docs/11): BootLoad/NvBackLTE/NvBackGU/BootRom×2/VxWorks/​/yaffs0/FastBoot/kernel//yaffs1/cdromiso; сверить с дампом устройства.

## 7. Ближайшие пять действий

1. Снять UART‑консоль (тестпоинты) и подтвердить вывод VxWorks — это ускорит всё дальше.
2. Карта флеша УЖЕ расшифрована из образа (docs/11): kernel @0x3300000/3 МБ, VxWorks @0x6A0000/32 МБ, BootLoad без A/B. Осталось: снять дамп с устройства и сверить с дефолтной таблицей (не заменялась ли ptable на устройстве).
3. Вызвать в shell `BSP_GetSupportBands` и записать точные бэнды (закрывает вопрос
   из docs/08 §4 окончательно).
4. Поднять toolchain soft‑float и собрать payload «UART hello» для проверки цикла.
5. Скачать GPL‑исходники 2.6.35.7 и оценить, какие драйверы Balong уже есть — это
   определит выбор базы ядра (vendor vs mainline).
